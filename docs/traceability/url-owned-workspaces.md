## Ownership Notes

- `src/projects/routes.ts`, `src/datasets/routes.ts`, and `src/administration/routes.ts` are the only
  family-owned route/link interfaces.
- `src/datasets/uploadLifecycle.ts` is the only classifier of a new dataset upload's request and
  task state, and `src/datasets/useDatasetUploadCommands.ts` is its only command owner; no upload
  screen holds a query client or issues the upload endpoint itself. `src/datasets/uploadBilling.ts`
  owns billing eligibility, the remembered choice, and subscription recovery, and neither module
  reads selected unit or organisation state. Adding a version to an existing dataset still runs
  through `src/components/uploads/ProgressBar.tsx` and has not been migrated; see the attachment
  note below for how a dataset version reaches a project.
- `src/datasets/attachment.ts` is the only place that decides which projects a dataset version may
  be attached to, how one is named, and how an attachment's input is shaped and its failure
  reported. Eligibility reads the generated project collection's own membership lists alone, so it
  crosses organisations and units and no billing unit narrows it; the generated organisation and
  unit indexes are read only to name a target's ancestry. It asks `src/projects/fileFacts.ts` what a
  project directory is rather than spelling out a second rule, and it decides nothing about where
  the caller is. `src/datasets/useDatasetAttachmentTargets.ts` is the only place those facts are
  gathered, and `src/datasets/useDatasetAttachmentCommands.ts` is the only owner of the attachment
  mutation and of the invalidation a settled attachment earns: the generated listing key of the
  target project's own directory and the generated dataset collection, and neither before the task
  has settled. No attachment screen holds a query client or a generated mutation of its own.
- `src/datasets/mutations.ts` owns what one settled Data Manager task means for this family, and
  `src/datasets/awaitDatasetTask.ts` is the only place a dataset _command_ waits for one and the only
  place one remembers the task its accepted work already has. Deletion and attachment both name the
  work they are waiting for and share that single settlement rule and that single ledger, so a done
  task with a non-zero or missing exit code can never read as success in one command and as a failure
  in the other, and neither can send work the Data Manager already accepted a second time. Uploads
  are not commands of this kind: a file's own record is polled by the screen holding it through
  `uploadLifecycle.ts`, and adding a version through `src/components/uploads/ProgressBar.tsx` has not
  been migrated at all.
- `src/administration/subscriptionFacts.ts` is the only place a generated product is read as a
  subscription: what kind it is, what it is called, what it costs, what claims it, and which
  organisation and unit own it. It judges no authority and reads no caller state. A product type
  this client has no rule for is `unrecognised` rather than assumed, so a regenerated client fails
  to compile here instead of quietly offering the wrong lifecycle for it.
  `src/administration/subscriptionCapabilities.ts` owns the named create, adjust, delete, and
  handoff evaluators, and shares the confirmed-facts rule `capabilities.ts` already stated rather
  than restating it. Each evaluator adds only what its own generated endpoint says beyond the one
  unit authority; none is ever hidden, because the generated product endpoints expose no
  exclusively platform-administrator action. The handoff evaluator asks
  `src/projects/projectCreation.ts` whether a project may still claim the subscription, so no screen
  judges that itself and Administration and Projects cannot disagree about which handoff is usable.
  `src/administration/useSubscriptionCommands.ts` is the only Administration owner of a generated
  product mutation and of the invalidation each one earns — the caller's product index, the
  addressed product, its unit, and its organisation. Projects keeps the creation and cleanup of the
  subscription its own workflow owns.
- `src/routing/` contains domain-neutral parsing and canonicalisation primitives only.
- `src/application/pagePolicy.ts` is the closed page-composition discriminant. It does not expose
  arbitrary layout, authentication, provider, or fallback flags.
- Every UI page entry attaches one policy with `withPagePolicy`; `_app` resolves it through
  `PagePolicyComposer` before rendering the page.
- `src/administration/capabilities.ts` is the only place that decides Administration authority. It
  reads generated resource facts and never reads organisation or unit names, and it exposes personal
  and default resolution as named predicates. `src/administration/accessFacts.ts` is the only place
  that gathers those facts, from the generated caller-account, default-organisation, and
  personal-unit resources; `src/hooks/useGetPersonalUnit.tsx` resolves the same way, so no screen
  identifies a personal unit by an organisation name.
- `src/administration/useAccessCommands.ts` is the only Organisation & access command owner and the
  only place that invalidates generated Account Server prefixes after a lifecycle command.
- `src/administration/inventoryFacts.ts` is the only place that decides what a usage report accounts
  for: which units a user works in and how many of their projects that user may change, which users
  one unit's report answers for, how the same read looks from the project's side, and what the
  report's own read established. It decides no authority and issues no read of its own.
  `src/administration/useUsageInventory.ts` is the only place the generated user-inventory endpoint
  is read, and it uses that endpoint's generated query options as its sole cache identity. An
  organisation report reads that organisation's own units from its generated resource rather
  than from the caller's index, so a unit of it the caller may read without belonging to still
  accounts for the users working in it. A confirmed refusal or absence is the report's own answer and is presented where the report is; a
  read that could not refresh a readable report leaves it on screen, marked stale and retryable in
  place; and only a transient read that established nothing reaches the task-level retry boundary.
  `src/administration/UsageInventory.tsx` is the only screen of these reports and holds no query
  client, no generated mutation, and no project-creation form: membership changes go to the
  addressed resource's own Organisation & access route through `organisationAccessOwner`, and every
  project role links that project's Manage route through `projectLinks` alone. The legacy global
  unit and organisation inventory routes, their feature views, and their table components are gone,
  and the remaining entry points that reached them address the canonical resource instead.
  `src/administration/AdministrationShell.tsx` presents the read-only tasks' boundary failures
  through `presentAdministrationFailure`, so a report that established nothing still says which
  transport fact stopped it, and `AddressedResourceView` in `src/administration/resources.tsx`
  is the one place an addressed Administration resource's pending, unavailable, and available
  states are rendered, shared by Organisation & access and by these reports.
- `src/projects/capabilities.ts` is the only place that decides project authority. Each retained
  project action has its own named pure evaluator reading the generated project resource, the
  caller's identity, and its billing state; `src/projects/projectFacts.ts` is the only place that
  gathers those facts, from the generated Data Manager account resource, the caller's realm roles,
  and the project workspace already resolved from the URL. Ordinary project authority comes from the
  project's own membership lists alone, so the Data Manager administrator role offers nothing but its
  own action. There is no shared permission engine and no global capability context, and the
  Administration and Projects evaluators share no code.
- `src/projects/resultFacts.ts` is the only place that decides which results belong to the addressed
  project and what the section may show for the reads it made, for a collection and for one
  addressed result alike. `src/projects/useProjectResults.ts` is the only Results composition hook;
  it uses the generated instance, task, and running-workflow query options as their sole cache
  identity and keeps no aggregate of its own. `src/projects/resultCapabilities.ts` adds only the
  result being looked at to the facts `projectFacts.ts` gathered, and the result evaluators live
  beside the other project evaluators in `src/projects/capabilities.ts`, so project authority still
  has exactly one owner. Capabilities are resolved per displayed result from that result's own
  owning project. `src/projects/useResultCommands.ts` is the only owner of Results mutations and of
  the generated invalidation that follows them: no Results component holds a query client or a
  generated mutation of its own, and every collection key the owner invalidates is built from a
  project's own list request, so no Results command can reach an unprojected collection. Result
  cards receive the owning project and their capabilities as props and build every link through
  `projectLinks`, so no card reads or changes global project scope.
- `src/projects/taskFacts.ts` is the only place that decides what one Results task's own facts mean:
  whether it is still running, finished, or unaccounted for, how often it is worth asking again, and
  what it produced. A summary the project's collection returned and the addressed task's own read go
  through the same rule, so a listed task and the one on its own route can never disagree about
  whether it has settled — which is the only thing deleting it depends on. Only a dataset task names
  a dataset there, because that is the only purpose whose identity the Data Manager promises. `src/projects/useResultTask.ts` is the only owner of that read and of the
  polling that follows it: the generated query is its sole cache identity, so the task it refreshes
  is the same one the owning project's Results refresh invalidates, and the poll's pace is decided
  by the task's lifecycle rather than by a timer that has to be told to stop. Deleting a task stays
  with `useResultCommands.ts` through `src/components/tasks/DeleteTaskButton.tsx`, which is the one
  place a task card or a task detail asks for that deletion.
- Each Results collection answers for itself all the way to the screen. `resultFacts.ts` classifies
  every read on its own and reports the section's outcomes as a pair rather than a single worst
  state, so a refused collection clears only its own content while a collection that merely could
  not be refreshed is the only one marked stale and is still offered its retry.
- `src/projects/sectionReads.ts` owns how one generated read is classified, how a group of them is
  reported, and what a section may show for each. Results and Run share it because the generated
  collections they read fail in exactly the same ways; neither section shares how it presents the
  outcome, and it decides no authority.
- `src/projects/runFacts.ts` is the only place that decides what the Run catalogue offers, which
  definition a canonical route addresses, and which of the addressed project's executions belong
  beside it. `src/projects/useProjectRun.ts` is the only Run composition hook; it uses the generated
  application, job, workflow, instance, and running-workflow query options as their sole cache
  identity and keeps no aggregate of its own. `src/projects/runCapabilities.ts` adds only the
  definition being looked at to the facts `projectFacts.ts` gathered, and the launch evaluator lives
  beside the other project evaluators in `src/projects/capabilities.ts`, so project authority still
  has exactly one owner. `src/projects/useRunCommands.ts` is the only owner of Run mutations and of
  the invalidation that follows them: no modal holds a query client or a generated mutation of its
  own, every collection key it invalidates is built from a project's own list request, and a launch
  is reported only after the Data Manager has accepted it. Run cards receive the addressed project
  and their capabilities as props and build every link through `projectLinks`, so no card reads or
  changes global project scope.
- `src/projects/fileFacts.ts` is the only place that canonicalises a project filesystem path,
  decides what one directory listing holds, and decides what the listing's own read established
  about it — including that a read still in flight has established nothing, which is what a
  directory that answered is told apart from. It classifies no read of its own and decides no
  authority: it names what `sectionReads.ts` classified, exactly as `resultFacts.ts` does for
  Results, and `capabilities.ts` receives the named value rather than the read state.
  `src/projects/routes.ts` reads and writes the `path`
  query through it alone, so a directory has exactly one URL and no other section can be handed the
  value. `src/projects/useProjectFiles.ts` is the only Files composition hook; it uses the generated
  file-and-path query options as their sole cache identity, with the URL project and the owned path
  as required arguments, and keeps no aggregate of its own.
  `src/projects/fileMutations.ts` is the only place that shapes a Files command's input and names
  its outcome — including which file a dataset may be made from and under what type, and which
  listings a move changes, which it takes from `fileFacts.ts` rather than walking a path of its own
  — and `src/projects/useFileCommands.ts` is the only owner of Files mutations and of the
  generated invalidation that follows them: no Files component holds a query client or a generated
  mutation of its own, and every listing key the owner invalidates is built from the addressed
  project's own request. The file-mutation evaluator lives beside the other project evaluators in
  `src/projects/capabilities.ts`, so project authority still has exactly one owner, and one
  capability governs the toolbar, the drop target, and every row action alike.
  `src/projects/fileFavourites.ts` keys favourites by project identity and takes the project as a
  required argument, so no favourite falls back to a selected project; `src/components/FileSelector`
  and the Files table read the same owner.
- `src/projects/developmentDefinitions.ts` is the only place a development-only definition enters the
  catalogue. It is empty outside development and adds nothing to any read, so no deployed catalogue
  depends on it.
- `src/projects/useProjectCommands.ts` is the only command owner for an existing project, and the
  only place that invalidates generated project prefixes after one of its commands. It holds every
  generated mutation that changes a project — privacy and all three membership lists included — so
  no other screen can reach one. Bringing a project into existence is the one project command it
  does not own, because that command spans two services and no project exists to address yet; see
  the project-creation note below.
  `src/projects/projectMutations.ts` is the only place that shapes a project command's input and
  names its outcome: it resolves the one membership change a list edit expresses and refuses to
  guess at more, and every command answers with a typed outcome rather than with words.
  `src/projects/failures.ts` owns how an authoritative rejection reads — including the sentence an
  unclassifiable transport fact shows, and the sentence a recoverable project-creation failure shows
  for whichever of the two services it was addressing — so no screen writes a rejection of its own
  and no project command navigates or changes scope in response to a server `403`.
- `src/projects/projectCreation.ts` is the only place that decides how a project comes into
  existence. It owns the cross-service lifecycle as one pure transition function, the eligibility of
  a containing unit and a tier, the validity of an optional subscription handoff, and the parsing,
  reconciliation, and forgetting of the recovery record kept under one exported session-storage key.
  It decides no project authority and reads no selected unit or organisation state. A subscription
  identity is promoted into lifecycle state before the project request is allowed to begin, which is
  what makes every retry reuse the subscription it already has rather than create a second one; and
  only a subscription this workflow created is ever cleaned up, so a handed-off one survives its
  cancellation as a released identity the attempt still names. Which flavours a request may carry
  comes from the generated request body, and the sentence a failed command shows comes from
  `failures.ts`; what this module still says in words is only why a handoff cannot be used, which is
  a fact about the addressed subscription rather than an answer to a command.
  `src/projects/useProjectCreationCommands.ts` is the only owner of the two creation
  mutations and the deletion that cancels them, and the only place that invalidates the generated
  unit, product, and project prefixes those commands affect; no creation screen holds a query client
  or a generated mutation of its own. `src/administration/AdministrationWorkspace.tsx` reads that
  module's unclaimed-subscription predicate to decide what it may offer, so Administration and
  Projects agree on which subscription is still claimable rather than each judging it separately.
- `src/projects/ProjectManageActions.tsx` is the only place project privacy and membership are
  changed. Each control reads the project in the URL, is offered only by its own capability, and
  presents every pending, rejected, failed, declined, and successful answer beside itself. The
  migrated inventory reports and the project stats actions link to that route instead of owning a
  second way to change the same facts.
- `src/projects/routes.ts` also owns the project file transport hrefs, and `readProjectFileAddress`
  is the one place a server entry turns request arguments into a project file. The Data Manager
  resource path is built once, from the file path the route itself carries, and reused by the
  server-rendered viewer, the browser viewer proxy, the download proxy, and the SDF parser, so no
  screen composes a project file URL of its own. `src/projects/fileViewers.ts` is the only place
  that decides which viewers a file offers, what each is called, which viewer a URL naming none
  means, whether the Data Manager holds the file compressed, and what the page established about
  the file before a viewer was framed; absence and refusal answer identically there and in the
  page's own response. `src/projects/ProjectFileViewer.tsx` is the only screen that shows a project
  file, and it decides nothing about the file's existence itself: the page's own answer is what it
  renders, so the server-rendered viewer paints without waiting on the browser, and a viewer that
  fetches its own bytes is never framed around a file that is absent or refused.
- `src/datasets/routes.ts` also owns the dataset version transport hrefs. The Data Manager resource
  path is built once and reused by the server-rendered viewer, the browser viewer proxy, and the
  download proxy, so no screen composes a dataset version URL of its own.
  `src/utils/api/viewerContent.ts` owns the one rule for what a viewer transport's answer means,
  because dataset versions and project files read the same transport and fail in the same ways;
  each family still owns what it discloses, so `src/datasets/viewerContent.ts` is the only place
  that makes a denied dataset version answer exactly as a missing one and `src/projects/fileViewers.ts`
  the only place that does so for a project file. `src/utils/api/plaintextViewerSSR.ts` reports transport facts only: the response
  status is the status, and an upstream message is never one.
- `src/utils/api/serverSidePropsError.ts` owns how a server-rendered failure reports itself. It
  decides the status line, so no upstream message can reach it and destroy the response, and it
  decides what a rejected transport says, so upstream text stays a Sentry diagnostic rather than
  page content.
- `src/api/runtime/classifyTransportFailure.ts` classifies transport facts only. Route families retain
  ownership of non-disclosing parent failures, local child failures, stale-data behavior, and rendering.
- `FamilyRouteBoundary` withholds named-family descendants until the router is ready and the family
  parser accepts a canonical relative href. Unknown query keys never appear in parsed route models and
  therefore cannot become generated query arguments. Legacy global scope hooks remain confined to the
  temporary plain `application` composition. A parse failure that names a parent the rendering
  section itself owns is that section's own child failure: the boundary keeps the section mounted and
  passes the named parent through, so a missing child never removes the parent along with it. The
  Projects family re-validates that parent through `localNotFoundProjectId` rather than trusting it.
